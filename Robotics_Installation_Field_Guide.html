The Robotics Software Installation Guide

The Robotics Software Installation Guide

From Bare Machine to Working Robot Lab
Every robotics course loses its first week to installation, and it is almost never because any single step is hard. It is because the steps have an order, that order is rarely written down, and one missed dependency five layers back produces an error message that points nowhere near the cause. This book is that order. It goes from a bare Ubuntu machine to a workstation that can talk to a robot, run ROS 2, drive a vendor SDK, and launch a simulator — verifying each layer before building on it, so that when something breaks you know exactly which floor it broke on.
A companion in the Field Guide series · the setup book for the ROS 2, G1 & Lucky Robots guides · offline, self-contained
This book is interactive Press Ctrl+K to search every heading; tick the sidebar checkboxes to track progress (or press R); use ←/→ to move chapter to chapter; toggle light/dark and text size top-right; hover any command block to copy it. Every chapter ends with a ⌨️ verification step — run it before moving on. That discipline is the entire method of this book. Everything works offline.

How to Read This Book — Front Matter

This is a procedure, not a reference. Read it in order the first time, run every verification step, and don't skip ahead to the interesting part — the interesting part depends on the boring parts being correct.

The journey, part by part The Order of Operations explains why sequence matters here more than in most software setup. Part I (The Foundation) is the operating system, the build toolchain, Git, and your editor. Part II (Reaching the Robot) is SSH and network configuration — the step that blocks more people than anything else. Part III (The Robotics Stack) is the actual robotics software: Python environments, ROS 2, vendor SDKs, simulators, and GPU drivers if you need them. Part IV (Making It Last) is verification, reproducing the setup on another machine, and troubleshooting — the part that turns a working machine into a working lab.
How to actually use it Keep a text file open and paste every command you actually run into it, along with anything you had to change. You will need that file in Chapter 12, and you will need it far sooner than you expect — the first time a machine gets wiped, or the first time a classmate asks how you got it working. This book installs the stack that the other robotics guides in this series assume: the ROS 2 guide, the Unitree G1 guide, and the Lucky Robots guide each pick up where their chapter here leaves off.

The Order of Operations — Front Matter

Robotics software is a stack where each layer assumes the one beneath it. Install out of order and you get errors that describe a symptom several layers away from the cause.

The three rules

  • The Ubuntu version determines everything above it. ROS 2 distributions are pinned to specific releases and vendor SDKs are built against specific Pythons. Pick the OS version last-to-first: decide what you need to run, then install the Ubuntu that supports it. Getting this wrong means reinstalling the machine.
  • Verify each layer before building on it. Ten minutes of checks saves a day of debugging a symptom whose cause is four layers down. Every chapter here ends with a verification step for exactly this reason.
  • Write down what you did. Not afterwards — as you go. See Chapter 12.
Do not start by pip-installing things The instinct when following a robotics tutorial is to run whatever pip install line it opens with. Resist it. Robotics stacks mix apt-installed system packages (ROS 2), pip packages, compiled dependencies (CycloneDDS), and vendor SDKs that pin specific versions of all of the above — and they interact. Installing pieces in an arbitrary order, into whatever Python happens to be active, produces a machine that works until it abruptly doesn't and that nobody can reconstruct. Follow the order in the diagram. It takes an afternoon and it holds up.

Part I — The Foundation

Choosing the OS — Chapter 1

This decision constrains everything else, and it is genuinely hard to change later. Spend ten minutes on it.

Ubuntu LTS, and which one

Robotics runs on Ubuntu. Not because it's better, but because it's what everything is built and tested against — ROS 2 targets it, vendor SDKs assume it, and every tutorial you'll follow was written on it. Using something else means porting, constantly, alone.

Pick the LTS that matches your ROS 2 distribution:

UbuntuROS 2Choose it when
24.04 LTS (Noble)Jazzy Jalisco (LTS, to 2029)Default for new setups
22.04 LTS (Jammy)Humble Hawksbill (LTS)Your lab or a required package is on Humble
26.04 LTSLyrical LuthOnly if you need it — the ecosystem lags

The rule: match whatever your lab, your robot's SDK, and your required packages use. Being one release ahead of your vendor SDK is a reliable way to spend a week compiling things.

Bare metal, dual boot, WSL, or a VM

OptionVerdict
Native / dual bootRecommended. Full hardware access, real networking, GPU works
WSL2Fine for learning ROS 2 and simulation. Networking to a physical robot is awkward; USB needs extra work
VMWorkable for coursework. Poor GPU, and bridged networking to a robot needs care
DockerExcellent for reproducibility once you know the stack. A poor first environment — it hides the layers you're trying to learn

If you'll connect to real robot hardware over Ethernet, native is worth the effort. Every virtualization layer between you and the network interface is somewhere multicast discovery can silently fail (ROS 2 guide, Chapter 10), and diagnosing that from inside a VM is genuinely unpleasant.

Verify — know what you're on 
lsb_release -a                 # Ubuntu version — must match your ROS 2 plan
uname -r                       # kernel
python3 --version              # the system Python
df -h /                        # at least 50 GB free; simulators are large
free -h                        # 8 GB RAM minimum, 16+ comfortable
Write these four values into your setup notes now. When something breaks in three weeks, "which Ubuntu, which Python" is the first question anyone will ask you.

Base System & Toolchain — Chapter 2

The compilers and build tools that everything above quietly assumes. Install them now, in one go, and you avoid a long sequence of interruptions later.

sudo apt update && sudo apt upgrade -y

# Build toolchain — vendor SDKs and DDS need to compile
sudo apt install -y build-essential cmake git curl wget \
    pkg-config software-properties-common

# Python — note python3-venv is SEPARATE on Debian/Ubuntu
sudo apt install -y python3 python3-pip python3-venv python3-dev

# Networking and diagnostics — you will need all of these
sudo apt install -y net-tools iproute2 iputils-ping \
    openssh-client tcpdump

# Quality of life
sudo apt install -y tmux htop tree unzip jq

Why these specifically

  • build-essential, cmake — CycloneDDS and most vendor SDKs compile from source. Without these you get a compiler error that reads like an SDK bug.
  • python3-venv — a separate package on Ubuntu, and the single most common missing piece behind "venv doesn't work" (Python guide, Chapter 2).
  • python3-dev — headers needed by any package with C extensions.
  • iproute2, tcpdump — you cannot debug a robot network without being able to see it (Chapter 5).
  • tmux — robotics is multi-terminal work, and over SSH it means a dropped connection doesn't kill your running node.
Verify — the toolchain works 
gcc --version && cmake --version && git --version
python3 -m venv --help | head -3      # must not error
ip link show                          # your network interfaces
If python3 -m venv --help errors, install python3-venv before going further. Everything in Part III depends on it.

Git & Your Editor — Chapter 3

Set these up before you write code, not after. Both take five minutes and both are worse to retrofit.

Git identity

git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase false

Use the email attached to your GitHub account so commits link to you. The Git & GitHub Field Guide covers the rest.

Verify — end to end 
mkdir -p ~/robotics-setup && cd ~/robotics-setup

Use this repo as your setup log. Every command you run from here on goes in it — that's Chapter 12 starting early, and it costs nothing now.

Part II — Reaching the Robot

SSH, Keys & Config — Chapter 4

SSH is how you reach every robot, lab machine, and single-board computer you'll work with. Doing it properly once removes an enormous amount of daily friction.

What SSH gives you

SSH opens an encrypted connection to another machine's shell. For robotics it's the backbone: a shell on the robot, file transfer, port forwarding to reach a dashboard running onboard, and the transport under VS Code's Remote-SSH.

Generate a key

Password authentication is fine once and tedious forever — and VS Code reconnects constantly. Use keys:

ssh-keygen -t ed25519 -C "you@example.com"
# Accept the default path. Set a passphrase.

ls -l ~/.ssh/
# id_ed25519       <- PRIVATE. Never leaves this machine. Never commit it.
# id_ed25519.pub   <- public. Safe to copy anywhere.

The mental model: the public key is a lock you can hand out freely; the private key is the only thing that opens it. Copy the public key to anything you want to log into:

ssh-copy-id unitree@192.168.123.164
ssh unitree@192.168.123.164          # no password now

ssh-agent

A passphrase on your key is correct, and typing it every connection is not. ssh-agent holds the unlocked key in memory for the session:

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
ssh-add -l                            # what the agent is holding

~/.ssh/config — the real quality-of-life win

Stop typing addresses and usernames. Define hosts once:

# ~/.ssh/config

Host g1
    HostName 192.168.123.164
    User unitree
    IdentityFile ~/.ssh/id_ed25519

Host labpc
    HostName lab-workstation.csusb.edu
    User yourname
    ForwardAgent yes

Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
chmod 600 ~/.ssh/config              # SSH refuses loose permissions
ssh g1                               # that's the whole command now

The Host * block sends a keepalive every 60 seconds, which stops idle sessions from dropping — worth having on any robot connection, and it's the difference between a stable VS Code Remote session and one that disconnects whenever you stop typing.

The bits you'll actually use

scp file.py g1:~/                    # copy TO the robot
scp g1:~/logs/run.csv ./             # copy FROM the robot
scp -r ./project g1:~/               # whole directory

ssh -L 8080:localhost:8080 g1        # robot's port 8080 -> your localhost:8080
ssh g1 'ls -l ~/logs'                # run one command without a session

ssh -v g1                            # verbose — the first debugging step

Port forwarding is worth knowing: it lets you open a web dashboard or visualiser running on the robot in your own browser, which is otherwise awkward on a robot with no screen.

Never commit a private key id_ed25519 without the .pub is the credential itself. Committing one to a repository — especially a public one — hands over access to everything that key opens, and automated scanners find them within minutes of a push. Add .ssh/, *.pem, and id_* to your global gitignore, and if you ever do push one, treat it as compromised: generate a new key and remove the old public key from every machine. Rotating is fast; deleting the commit is not sufficient, because the history is already out there. The Git guide's security chapter covers secret handling generally.
Verify — passwordless in one word 
ssh g1 'hostname && whoami && uname -a'
One command, no password prompt, output from the remote machine. If that works, VS Code Remote-SSH will work too — and if it doesn't, fix it here rather than debugging it through an editor.

Robot Network Setup — Chapter 5

Robots generally don't run DHCP. Nothing works until you assign yourself an address on their subnet by hand, and this is where most first sessions stall.

The situation

Most robots present a fixed internal network on a known subnet with no DHCP server. Plug in and your machine gets no address, so it cannot reach anything. You have to configure one yourself.

ip link show                     # find the wired interface: enp2s0, eth0...

# Temporary — cleared on reboot. Ideal for a lab session.
sudo ip addr add 192.168.123.99/24 dev enp2s0
sudo ip link set enp2s0 up

ip addr show enp2s0              # confirm the address is there
ping -c 3 192.168.123.161        # can you reach the robot?

For the Unitree G1 the subnet is 192.168.123.0/24; specific addresses are in the G1 guide, Chapter 2. Other robots differ — check their documentation for the subnet and pick a free address on it.

Making it persistent

Retyping that every boot gets old. With NetworkManager:

nmcli connection add type ethernet ifname enp2s0 con-name robot-net \
    ip4 192.168.123.99/24
nmcli connection up robot-net

nmcli connection show                    # list profiles
nmcli connection down robot-net          # switch back off

A named profile you can bring up and down is better than editing your default connection, because you'll want normal internet on the same interface at other times.

Diagnosing

ip addr show                     # do I have an address on the right subnet?
ip route                         # where does traffic actually go?
ping -c 3 192.168.123.161        # basic reachability
arp -n                           # who has responded on this segment?
sudo tcpdump -i enp2s0 -n        # is anything on the wire at all?

Work in that order. If ping fails, nothing above it in the stack can possibly work, and debugging your SDK is wasted effort until it succeeds.

Two networks at once You'll often want the robot's subnet on Ethernet and internet on Wi-Fi at the same time. That works, but watch the routing: if the robot connection advertises a default route, your internet traffic may try to go through the robot and simply stop working. Assign the robot interface an address with no gateway (as above — note there's no gw in that nmcli command), so it's used only for its own subnet. Check with ip route that your default route still points at Wi-Fi. This catches people every single semester, and it presents as "the internet broke when I plugged in the robot", which sounds unrelated and isn't.
Verify — the layer that everything depends on 
ip addr show enp2s0 | grep inet     # address on the robot subnet
ping -c 3 192.168.123.161          # robot responds
ip route | head -3                 # default route still goes to the internet
ssh g1 'hostname'                  # and you can log in
All four must pass before Part III. Every problem in the rest of this book is easier to diagnose when you know the network is sound.

Part III — The Robotics Stack

Python Environments — Chapter 6

Set the pattern now, before any robotics package is installed. Retrofitting isolation onto a machine where everything went into the system Python is genuinely painful.

The rule

One virtual environment per project, named .venv, in the project root, gitignored:

mkdir -p ~/robotics/myproject && cd ~/robotics/myproject
git init
python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade pip
python -m pip --version               # confirm it's the venv's pip

echo ".venv/" >> .gitignore

Use python -m pip install rather than bare pip install — it guarantees the installer and interpreter match, which structurally prevents the most common Python error. The Python Environment Field Guide makes the full case.

The robotics exception

ROS 2's Python packages are installed system-wide by apt and a normal isolated venv cannot see them — import rclpy will fail. When a project needs both ROS 2 and its own pip packages, source ROS first and create the venv with system packages visible:

source /opt/ros/jazzy/setup.bash                  # 1. ROS first
python3 -m venv --system-site-packages .venv      # 2. venv that can see it
source .venv/bin/activate                         # 3. then activate

Order matters. Reverse steps 1 and 3 and you'll be back on the system Python without noticing.

Verify — isolation actually works 
source .venv/bin/activate
python -c "import sys; print(sys.executable); print(sys.prefix)"
# both must point inside your .venv

python -m pip install requests
python -c "import requests; print(requests.__file__)"
deactivate
python3 -c "import requests"        # ModuleNotFoundError — correct!
That final error proves the isolation is real. If requests imports after deactivating, you installed into the system Python and should sort that out now rather than later.

Installing ROS 2 — Chapter 7

System-wide via apt, matched to your Ubuntu version. Skip this chapter if your robot's SDK speaks DDS directly and you don't need the ROS ecosystem.

# Locale — ROS 2 needs a UTF-8 locale
sudo apt update && sudo apt install -y locales
sudo locale-gen en_US en_US.UTF-8
sudo update-locale LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8
export LANG=en_US.UTF-8

# Enable the universe repository
sudo apt install -y software-properties-common curl
sudo add-apt-repository universe

# Add the ROS 2 apt source. This is the CURRENT method: a small .deb that
# configures the repository and its signing key for you. Older guides tell you
# to curl ros.key into /usr/share/keyrings by hand — that approach is superseded.
export ROS_APT_SOURCE_VERSION=$(curl -s \
  https://api.github.com/repos/ros-infrastructure/ros-apt-source/releases/latest \
  | grep -F "tag_name" | awk -F'"' '{print $4}')
curl -L -o /tmp/ros2-apt-source.deb \
  "https://github.com/ros-infrastructure/ros-apt-source/releases/download/${ROS_APT_SOURCE_VERSION}/ros2-apt-source_${ROS_APT_SOURCE_VERSION}.$(. /etc/os-release && echo ${UBUNTU_CODENAME:-${VERSION_CODENAME}})_all.deb"
sudo dpkg -i /tmp/ros2-apt-source.deb

# Install
sudo apt update && sudo apt upgrade -y
sudo apt install -y ros-jazzy-desktop ros-dev-tools

# Source it — required in EVERY new terminal
source /opt/ros/jazzy/setup.bash

An alias instead of .bashrc

Adding the source line to ~/.bashrc is convenient and has a cost: it affects every terminal you ever open, including ones where you want a clean environment or a different distribution. An alias keeps it explicit:

echo "alias sj='source /opt/ros/jazzy/setup.bash'" >> ~/.bashrc
source ~/.bashrc
Verify — talker and listener 
source /opt/ros/jazzy/setup.bash
ros2 --help
printenv | grep -i ros            # ROS_DISTRO should be set

# Terminal 1:
ros2 run demo_nodes_cpp talker
# Terminal 2 (source again first):
ros2 run demo_nodes_py listener
# Terminal 3:
ros2 topic list && ros2 topic hz /chatter
Messages flowing between the two means the install and the DDS layer are both working. Continue in the ROS 2 guide.

Vendor SDKs — Chapter 8

Where installs get fragile. Vendor SDKs pin specific versions of compiled dependencies, and their error messages rarely name the real problem.

The Unitree SDK, as a worked example

cd ~
git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
cd unitree_sdk2_python
pip3 install -e .

This commonly fails, because it needs cyclonedds 0.10.2 specifically. Build it and point the SDK at it:

cd ~
git clone https://github.com/eclipse-cyclonedds/cyclonedds -b releases/0.10.x
cd cyclonedds && mkdir build install && cd build
cmake .. -DCMAKE_INSTALL_PREFIX=../install
cmake --build . --target install

export CYCLONEDDS_HOME=~/cyclonedds/install
echo 'export CYCLONEDDS_HOME=~/cyclonedds/install' >> ~/.bashrc

cd ~/unitree_sdk2_python && pip3 install -e .

This is why Chapter 2 installed build-essential and cmake — without them the cmake step fails with an error that looks like an SDK problem.

The general pattern

  • Read the vendor's README first, all of it, before running anything. The prerequisites are usually stated and usually skipped.
  • Note the pinned versions — Python version, numpy version, DDS version — and honour them exactly. Upgrading numpy because something else wanted a newer one is a classic way to break a working robot setup.
  • Install into a venv, not system-wide, so a bad install is one rm -rf away from gone.
  • Use pip install -e . for cloned SDKs — editable installs let you read and patch the source, which you will end up doing.
  • Record the commit you cloned. "The SDK from GitHub" is not a version; git rev-parse HEAD is.
Verify — import and connect 
python -c "import unitree_sdk2py; print(unitree_sdk2py.__file__)"
echo $CYCLONEDDS_HOME
cd ~/unitree_sdk2_python && git rev-parse --short HEAD   # record this
Then run the read-only subscriber from the G1 guide, Chapter 3 against a real robot. Importing proves the install; receiving state proves the whole stack.

Simulation — Chapter 9

Install a simulator even if you have hardware — especially if you have hardware. It's where you'll do most of your actual iterating.

# Lucky Engine: download from luckyrobots.com, then:
source .venv/bin/activate
pip install luckyrobots
export LUCKYENGINE_PATH=/path/to/LuckyEngine
echo 'export LUCKYENGINE_PATH=/path/to/LuckyEngine' >> ~/.bashrc

# Plain MuJoCo, if you want the physics engine on its own:
pip install mujoco
python -m mujoco.viewer                 # opens a viewer window

# Gazebo, if you're working in ROS 2:
sudo apt install -y ros-jazzy-ros-gz

Simulators are large and pull in heavy dependencies, so this is exactly the situation venvs exist for. The Lucky Robots guide continues from here.

Verify — connect to the engine 
python -c "
from luckyrobots import Session
with Session() as s:
    s.connect(timeout_s=30.0)
    info = s.get_model_info()
    print('nq', info.nq, 'nu', info.nu)
"
Launch the engine first. Joint counts printing means the install, the path variable, and the gRPC connection are all correct.

GPU & CUDA — Chapter 10

Only if you need it. GPU setup is the most brittle part of any robotics install, and a great many projects never require one.

Do you actually need this?

You need a GPU forYou don't for
Training deep networks / RL policiesControl loops and classical robotics
Real-time vision models on videoROS 2, DDS, most SDK work
Isaac Sim and photorealistic renderingMuJoCo state-based simulation
Large local language modelsCalling a hosted model API

If you're not in the left column, skip this chapter. Installing CUDA "just in case" is a common way to break a working machine.

Driver first, always

ubuntu-drivers devices                    # what does Ubuntu recommend?
sudo ubuntu-drivers autoinstall
sudo reboot

nvidia-smi                                # driver version + CUDA capability

nvidia-smi reporting your card means the driver is working. That's the layer to get right before anything else; most CUDA problems are actually driver problems.

CUDA via the framework, not by hand

Modern PyTorch ships its own CUDA runtime. Installing the CUDA toolkit system-wide is usually unnecessary and is a reliable source of version conflicts:

pip install torch --index-url https://download.pytorch.org/whl/cu124
python -c "import torch; print(torch.cuda.is_available(), torch.version.cuda)"

True means you're done. Only install the full toolkit if you're compiling CUDA code yourself.

Do not chase CUDA versions The compatibility matrix between driver, CUDA runtime, PyTorch, and any given framework is genuinely fiddly, and the standard failure is a spiral: install a different CUDA to satisfy one package, break another, install a third, end up with a machine nobody can reason about. Install the driver, then let the framework bring its own CUDA. If two packages genuinely need incompatible CUDA versions, that's what separate virtual environments — or conda, which can manage CUDA runtimes per environment — are for. Do not try to satisfy both system-wide. And if a GPU setup does get into an unexplainable state, reinstalling the driver cleanly is faster than diagnosing it.

Part IV — Making It Last

Verify Everything — Chapter 11

Run the whole stack top to bottom before you declare the machine ready. Finding a gap now costs minutes; finding it during a lab session costs the session.

The full sweep

echo "=== System ==="
lsb_release -d && uname -r && python3 --version

echo "=== Toolchain ==="
gcc --version | head -1 && cmake --version | head -1 && git --version

echo "=== Network ==="
ip -brief addr show
ip route | head -3

echo "=== SSH ==="
ssh -o BatchMode=yes g1 'hostname' || echo "SSH to robot FAILED"

echo "=== Python ==="
source ~/robotics/myproject/.venv/bin/activate
python -c "import sys; print(sys.executable)"

echo "=== ROS 2 ==="
source /opt/ros/jazzy/setup.bash
ros2 --version && echo "ROS_DISTRO=$ROS_DISTRO"

echo "=== SDK ==="
python -c "import unitree_sdk2py; print('SDK ok')" 2>/dev/null || echo "SDK not available"

echo "=== Sim ==="
python -c "import luckyrobots; print('luckyrobots ok')" 2>/dev/null || echo "sim not available"

Save that as verify.sh in your setup repo. Run it after any significant change, and on any new machine. Knowing precisely which line fails is worth far more than a general sense that something is wrong.

Imports are not proof. Each layer has a test that actually exercises it:

Reproducing the Setup — Chapter 12

A working machine that only one person can rebuild is a liability with a deadline attached. This chapter turns it into an asset.

What to capture

  • The exact commands you ran, in order, in a script. Not prose — runnable lines.
  • Versions of everything: Ubuntu, Python, ROS distro, SDK commit hash, simulator build.
  • requirements.txt from every venv, pinned.
  • Config files: ~/.ssh/config (without keys), network profiles, CycloneDDS XML.
  • Environment variables you set: CYCLONEDDS_HOME, LUCKYENGINE_PATH, ROS_DOMAIN_ID.
  • The things that went wrong and what fixed them. This is the most valuable part and the part everyone omits.
cd ~/robotics-setup

# Capture the current state
source ~/robotics/myproject/.venv/bin/activate
pip freeze > requirements.txt

{
  echo "# Environment"
  lsb_release -d
  python3 --version
  echo "ROS_DISTRO=$ROS_DISTRO"
  echo "SDK commit: $(cd ~/unitree_sdk2_python && git rev-parse --short HEAD)"
} > VERSIONS.md

git add -A && git commit -m "Capture working setup"

The rebuild test

The only way to know your notes are sufficient is to use them. On a spare machine, a VM, or a fresh container, follow your own setup.sh and nothing else. You will find something missing — almost everyone does, usually a package installed months ago and forgotten. Fix the script, and now it's real.

From the field — the working state is the asset A configured robotics machine represents real accumulated knowledge: which versions coexist, which environment variable was needed, which dependency had to be built from source, and the thirty minutes someone lost discovering it. That knowledge lives in exactly one place — a hard drive — until you write it down. Machines get wiped, students graduate, and the person who set it up is unreachable the week of the demo. Labs that keep a working setup.sh in version control recover from a dead machine in an hour. Labs that don't lose days reconstructing a configuration nobody fully understood, and they lose them at the worst possible moment, because that's when the machine's condition finally matters enough to notice. The cost of capturing it is twenty minutes while everything is fresh. The cost of not capturing it comes due on someone else's deadline.

Troubleshooting — Chapter 13

Install problems, organized by the layer they actually live on rather than the layer that reported them.

Diagnose downward

Errors surface at the top of the stack and are caused near the bottom. When something fails, test downward from the failure until you find a layer that works — the fault is in the layer just above it.

python -c "import unitree_sdk2py"    # fails? test lower:
python -c "import sys; print(sys.executable)"   # right environment?
ping 192.168.123.161                            # network up?
ip addr show                                    # address assigned?

Verification Checklist — Appendix B

Print this. Work down it in order. Do not proceed past a failure — everything above depends on everything below.

Foundation

  • ☐ lsb_release -a shows the Ubuntu version your ROS 2 distro requires
  • ☐ gcc --version, cmake --version, git --version all respond
  • ☐ python3 -m venv --help does not error
  • ☐ git config --list shows your name and email
  • ☐ code --version responds; Remote-SSH extension installed

Reaching the robot

  • ☐ ls ~/.ssh/id_ed25519.pub exists; private key is not in any repo
  • ☐ ssh g1 'hostname' works with no password prompt
  • ☐ ip addr show shows an address on the robot's subnet
  • ☐ ping -c 3 <robot> succeeds
  • ☐ ip route — default route still points at your internet connection

The stack

  • ☐ sys.executable inside the venv points into .venv
  • ☐ A package imports inside the venv and fails after deactivate
  • ☐ ros2 --version responds after sourcing; ROS_DISTRO is set
  • ☐ talker and listener exchange messages
  • ☐ import unitree_sdk2py succeeds; CYCLONEDDS_HOME is set
  • ☐ Read-only subscriber receives live robot state
  • ☐ Simulator connects and prints joint counts
  • ☐ (If needed) nvidia-smi and torch.cuda.is_available() both good

Making it last

  • ☐ setup.sh in version control with every command you ran
  • ☐ requirements.txt committed from every venv
  • ☐ VERSIONS.md records Ubuntu, Python, ROS distro, SDK commit
  • ☐ Problems you hit and their fixes written down
  • ☐ verify.sh saved and passing
  • ☐ The rebuild test done on a second machine or VM
From the field — the method, not the commands The specific commands in this book will age. Ubuntu will move on, ROS 2 will release a new distro, the Unitree SDK will restructure, and some of these lines will need adjusting within a year. The method won't. Install in dependency order, bottom-up. Verify each layer before building on it. Diagnose downward from a failure until you find a layer that works. Write down what you did while you still remember it. That method applies to any robotics stack, any vendor, any year — and it's the actual difference between an engineer who can set up a lab and one who can only follow a tutorial that happens to still be accurate. The commands are worth having; the four sentences above are worth learning.
A closing word Installation is the least glamorous part of robotics and it consumes a genuinely absurd share of the field's collective time — largely because it's treated as a preliminary rather than as work, so nobody documents it and everybody redoes it. Treating it as work is the whole trick: an order, a verification at each step, and notes good enough that someone else could follow them. Do that once, properly, and you get a machine that keeps working and can be rebuilt in an hour instead of a day. You also get something less obvious but more useful — a real understanding of how the layers fit together, which is exactly the knowledge that lets you debug the strange failure six weeks from now. Then close this book and go do the robotics.
