The Lucky Robots Field Guide

Lucky Engine & Simulation-First Robotics
Robot hardware is scarce, slow, and breakable. Every hour on a real humanoid costs you setup, charge, and the risk that a sign error snaps a gearbox — and you get one run per attempt. Simulation inverts all of that: thousands of runs, perfectly repeatable, nothing to break. Lucky Engine is a simulator built specifically for that job, pairing MuJoCo physics with a game engine’s editor and rendering, driven from Python. This book covers getting it running, controlling robots inside it, generating training data at scale, and — the part that matters most — being honest about what simulation does and doesn’t prove.
A companion in the Field Guide series · pairs with the Unitree G1 & ROS 2 guides · offline, self-contained
This book is interactive Press Ctrl+K to search every heading; tick the sidebar checkboxes to track progress (or press R); use ←/→ to move chapter to chapter; toggle light/dark and text size top-right; hover any command block to copy it. Look for ⌨️ Try it boxes — every one of them runs on a laptop with no robot involved, which is rather the point. Everything works offline.
A moving target Lucky Engine and the luckyrobots SDK are actively developed, and the API surface described here reflects the current generation at the time of writing. Class names, method signatures, and available robots change between releases. Treat the code in this book as the shape of the thing, not as a specification. Check help() on the objects, read the version's own README, and trust the installed package over any book — including this one — when they disagree. The concepts (a stepped physics loop, policy slots, Gymnasium environments, sim-to-real) are stable; the exact spellings are not.

How to Read This Book — Front Matter

This is a short book about a tool, wrapped around a longer argument about method. The tool is Lucky Engine; the method is doing your robotics work in simulation first, and knowing exactly how far that gets you.

The journey, part by part Part I (Getting Running) is what Lucky Engine is, how to install and connect to it, and how scenes are put together. Part II (Driving the Simulation) is the core programming model: sessions, the step loop, controlling robots through policies or raw actuators, and getting observations back out. Part III (Doing Real Work) is where it earns its keep — reinforcement-learning environments, recording datasets for imitation learning, system identification, and an honest chapter on the sim-to-real gap. Part IV is troubleshooting, labs, and reference.
How to actually use it Read Chapter 10 early, even out of order. Simulation's failure mode isn't that it doesn't work — it's that it works beautifully and convinces you that something is finished when it isn't. Knowing what you're not being told is the difference between simulation as a tool and simulation as a trap. If you're using this alongside a real G1, the G1 guide's simulation chapter covers where the two workflows meet.

Part I — Getting Running

What Lucky Engine Is — Chapter 1

A game engine built for robotics rather than games — which turns out to be a genuinely useful combination, and explains most of its design.

The pieces

Lucky Engine pairs two things that are usually separate:

  • MuJoCo physics — the contact and dynamics engine that has become the research standard for legged and manipulation work. Accurate contact is the hard part of simulating a robot, and this is what MuJoCo is good at.
  • A game engine's presentation layer — Vulkan rendering for realistic camera feeds, a drag-and-drop scene editor, and C# scripting for in-engine behaviour.

You drive it from outside over gRPC, using the luckyrobots Python SDK. The engine runs as its own process; your Python program connects to it, steps physics, sends commands, and reads observations back. That separation matters: your training code and the simulator are decoupled, so you can restart one without the other.

Why the rendering matters

For a controller that only reads joint angles, rendering is irrelevant. But an increasing share of robot learning is vision-based — the policy takes camera images as input. If your simulated camera produces images that look nothing like the real one, a policy trained on them will fail on hardware for reasons that have nothing to do with your control logic. Realistic rendering is not cosmetic here; it's part of the physics of the problem you're solving.

What it's for

UseWhy simulation wins
Generating training dataMillions of labelled episodes. Physically impossible to collect otherwise
Testing control code safelyA sign error is a funny video, not a broken gearbox
Iterating without hardwareThe robot is shared, charging, or broken. Your laptop isn't
Reproducible experimentsIdentical initial conditions every run — hardware can never do this
Deterministic recordingHigh-rate labelled capture for offline analysis

Supported robots span quadrupeds, humanoids including the Unitree G1, manipulators, and anything else describable as a MuJoCo XML model — which in practice means most research robots.

Installing & Connecting — Chapter 2

Two halves: the engine, which is a downloaded application, and the Python client, which is a pip package. They find each other over a local network port.

Install

# 1. Download Lucky Engine for your platform (Linux, Windows, macOS)
#    from luckyrobots.com — free for research and personal use.

# 2. Install the Python client, in a virtual environment
python3 -m venv .venv && source .venv/bin/activate
pip install luckyrobots

# 3. Tell the client where the engine lives
export LUCKYENGINE_PATH=/path/to/LuckyEngine        # Linux / macOS
# set LUCKYENGINE_PATH=C:\path\to\LuckyEngine.exe   # Windows

Put that export in your shell profile. Forgetting it in a new terminal is the most common first-run failure, and the error it produces is not always obvious about the cause.

Use a virtual environment luckyrobots pulls in gRPC, numpy, and Gymnasium, all of which are version-sensitive and all of which other robotics tooling also depends on — often at different versions. Installing it into your system Python is a reliable way to break something else later, and modern Python will refuse anyway. One venv per project, as always: the Python Environment Field Guide covers the mechanics, and this is exactly the situation it exists for.

Connecting

The engine exposes a gRPC server, by default on 127.0.0.1:50051. The simplest connection test:

from luckyrobots import Session

with Session() as sess:
    sess.connect(timeout_s=30.0)
    info = sess.get_model_info()
    print(f"nq={info.nq}  nu={info.nu}  joints={len(info.joints)}")

Two numbers worth understanding from the start, because they come straight from MuJoCo and appear everywhere:

SymbolMeaning
nqSize of the position state vector — the model's generalized coordinates
nuNumber of actuators — how many things you can actually command

nq and nu are usually not equal, and expecting them to be is a common early confusion. A free-floating humanoid base contributes seven values to nq (position plus quaternion) that no actuator drives directly — you can't command the robot's world position, only its joints.

Try it — prove the connection 
# 1. Launch Lucky Engine.
# 2. In your venv:
python -c "
from luckyrobots import Session
with Session() as s:
    s.connect(timeout_s=30.0)
    info = s.get_model_info()
    print('nq', info.nq, 'nu', info.nu)
    for j in info.joints[:10]:
        print(' ', j)
"
Do this before anything else. If the joint names print, your install, path variable, and gRPC connection are all correct. If it times out, the engine isn't running or isn't listening where the client expects — fix that before writing any control code (Chapter 11).

The Editor & Scenes — Chapter 3

A scene is a world plus the robots in it. The editor is how you build one without writing XML by hand — which is more valuable than it sounds, because most of the fiddly work in simulation is scene setup.

What a scene contains

  • The robot — its MuJoCo model: links, joints, actuators, collision geometry, mass properties.
  • The environment — ground, obstacles, objects to manipulate, walls.
  • Lighting and materials — which determine what simulated cameras see, and therefore matter for vision policies.
  • Cameras — positioned to match the robot's real sensors as closely as you can manage.
  • Physics settings — timestep, solver parameters, friction and contact properties.

MuJoCo XML underneath

Whatever the editor shows you, the model is MuJoCo XML (MJCF) underneath. This is worth knowing for two reasons. First, it means the enormous existing library of MuJoCo robot models applies — including community G1 models. Second, when you need precision the editor doesn't offer, you edit the XML directly, and everything you learn about MJCF transfers to plain MuJoCo, Isaac, and most of the research literature.

Timestep and determinism

Physics advances in fixed discrete steps. The timestep trades accuracy against speed: smaller steps model fast contact more accurately and run slower. If a simulation behaves oddly — objects passing through each other, a robot jittering or exploding — an over-large timestep is among the first things to suspect.

The related property is determinism: same model, same initial state, same actions, same result, every time. This is the thing hardware can never give you, and it's what makes simulation scientifically useful — you can change exactly one variable and attribute the difference to it. Preserve it deliberately: seed your random number generators, and be suspicious of anything that introduces nondeterminism, because you're giving up simulation's main advantage.

Part II — Driving the Simulation

Sessions & the Step Loop — Chapter 4

Everything in Lucky Engine runs through a session and a loop: send actions, advance physics, read observations, repeat. Every other API in this book is a convenience layered on that.

The Session

from luckyrobots import Session

with Session() as sess:
    sess.connect(timeout_s=30.0)
    info = sess.get_model_info()

    for _ in range(1000):
        obs = sess.step(actions)          # advance one physics tick

Use the context-manager form. A session holds a gRPC connection and engine-side resources, and with guarantees they're released even when your code raises — the same argument as try/finally around robot motion in the G1 guide. A leaked session leaves the engine in a state you'll have to restart to clear.

The loop is the whole model

Simulation time only advances when you step it. This is the mental shift from hardware and it has consequences worth stating plainly:

  • Your code is never "too slow" — the world waits for you. A debugger breakpoint pauses physics, which is enormously useful and impossible on a real robot.
  • Nothing happens between steps. No interpolation, no drift.
  • Faster-than-real-time is normal. Without rendering, physics runs far quicker than the wall clock, which is what makes large-scale training feasible.
  • The step count is the clock. Simulated seconds are steps × timestep, unrelated to how long your program actually ran.

Async

The SDK provides AsyncSession and async controller mirrors for asyncio-native code. Useful when the simulator is one of several things you're awaiting — a model API, a web dashboard, several environments at once. If you're writing a straightforward training loop, the synchronous form is simpler and there's no reason to reach for async.

Robots, Policies & Actuators — Chapter 5

Two levels of control, and the distinction closely mirrors the high-level/low-level split on real hardware — which is not a coincidence.

Policies — the high-level route

The engine ships in-engine policies: controllers that already know how to do something, like walking. You hand them commands rather than joint targets:

from luckyrobots import Session

with Session() as sess:
    sess.connect(timeout_s=30.0)
    robot = sess.robot("G1")

    with robot.policy_slot("Walker"):
        robot.commands("Walker")["SetVx"] = 0.5      # forward velocity
        for state in robot.stream_state(target_fps=30):
            print(state.motion_graph_active)

A policy slot is an active controller occupying a control channel; the context manager acquires and releases it cleanly. This is the direct analogue of LocoClient.Move() on a real G1 — you're asking for a velocity and letting something else work out the joint trajectories.

Actuators — the low-level route

For direct control, address actuators by name through the MuJoCo scene:

scene = sess.scene()
scene.set_control(named={
    "left_shoulder_pitch": 0.3,
    "left_elbow": -0.5,
})

Use names, not indices. Index ordering changes when a model is edited, and an index-based script that silently drives the wrong joint after someone adjusts the scene is a genuinely nasty bug — the same hazard as joint indexing on real hardware (G1 guide, Chapter 6), minus the broken gearbox. Discover what's available rather than assuming:

sess.list_robots()
sess.list_policies()
info = sess.get_model_info()
for j in info.joints:
    print(j)

Which to use

Use a policy whenUse actuators when
You want locomotion that works, nowYou're writing the controller yourself
Testing behaviour above the walking layerDoing torque or impedance control
Generating demonstrations of normal motionReproducing a hardware controller exactly
You want the sim to match high-level hardware controlYou want the sim to match rt/lowcmd

Cameras & Observations — Chapter 6

What your policy can see determines what it can learn. Getting observations right — and honest — is more consequential than most people expect.

Kinds of observation

  • Proprioception — joint positions, velocities, torques; the robot's sense of its own body. Cheap, low-dimensional, and available on real hardware.
  • IMU — orientation and angular velocity of the base. Essential for anything balancing.
  • Cameras — rendered RGB or depth from any viewpoint in the scene.
  • Privileged state — exact object positions, ground-truth contact forces, the robot's true world pose.
Privileged information is the classic simulation trap Simulation can tell you things reality cannot: the exact position of an object, the true friction coefficient, perfect noiseless joint velocity. It is very easy to write a policy that quietly depends on one of these, get excellent results, and discover on hardware that the input simply doesn't exist. Before training anything, write down every observation your policy reads and confirm each one has a real sensor behind it. If it doesn't, either remove it or plan explicitly for how you'll estimate it. There is a legitimate advanced technique — privileged learning, where a teacher policy uses ground truth and distils into a student that uses only real sensors — but that's a deliberate design, not an accident. Accidental privileged information is the single most common reason a policy that works in sim fails completely in the real world.

Matching your real sensors

If the plan is to deploy on hardware, the simulated sensors should resemble the real ones. That means matching camera resolution, field of view, and mounting position; matching update rates (a policy trained on 100 Hz observations will struggle at 30 Hz); and adding noise, because real sensors are noisy and a policy trained on perfect data is brittle to imperfection. Deliberately degrading your simulated sensors feels wrong and is one of the highest-value things you can do for transfer.

Part III — Doing Real Work

Training with LuckyEnv — Chapter 7

LuckyEnv wraps the simulator in the Gymnasium interface, which means every off-the-shelf reinforcement-learning library works with it unmodified.

The Gymnasium contract

Gymnasium is the standard interface for RL environments, and it is deliberately tiny: reset() returns a starting observation; step(action) returns (observation, reward, terminated, truncated, info). That's the whole thing. Because it's standard, algorithms from Stable-Baselines3 and similar libraries plug straight in.

from luckyrobots import LuckyEnv


def my_reward(signals):
    return (2.0 * signals.get("track_linear_velocity", 0)
            + 1.5 * signals.get("track_angular_velocity", 0)
            - 0.01 * signals.get("action_rate", 0))


env = LuckyEnv(
    robot="unitreego2",
    scene="velocity",
    reward_fn=my_reward,
    reward_terms=["track_linear_velocity", "track_angular_velocity", "action_rate"],
    termination_terms=["fell_over", "time_out"],
)

obs, info = env.reset()
for _ in range(100_000):
    action = policy(obs)
    obs, reward, terminated, truncated, info = env.step(action)
    if terminated or truncated:
        obs, info = env.reset()

Reward design is the actual work

The reward function is where nearly all your time will go, and it is genuinely hard. The policy optimizes exactly what you wrote, not what you meant, and the gap between those two things is where reinforcement learning gets its reputation.

Note the shape of the example above — it's the standard locomotion pattern and worth understanding as a template:

  • Positive terms for the task — tracking the commanded velocity. This is what you want.
  • Negative terms for cost — action_rate penalizes jerky commands, producing smoother motion that's kinder to real hardware.
  • Weights that balance them — the coefficients are the tuning, and small changes can qualitatively change the learned behaviour.

Watch for reward hacking: the policy finding a way to score well that isn't what you intended — vibrating in place to exploit a velocity term, or falling in a way that happens to end episodes profitably. Always watch the learned behaviour rather than trusting the reward curve. A rising reward curve attached to an absurd-looking policy is a very common experience, and the curve is not the thing you care about.

Terminated vs truncated

These mean genuinely different things and conflating them corrupts learning. Terminated means the episode ended because of the task — the robot fell over; that's a real outcome the policy should learn from. Truncated means it hit a time limit — an artefact of your setup, not a failure. Bootstrapping value estimates incorrectly across these two is a subtle bug that produces a policy which mysteriously underperforms, so let the library handle them separately and don't collapse them into one flag.

Recording Datasets — Chapter 8

Not all robot learning is reinforcement learning. A great deal of current practice is imitation learning — collect demonstrations, fit a model to them — and that needs data in a standard format.

Why record

Imitation learning sidesteps reward design entirely: instead of specifying what good behaviour scores, you show examples of it. That's often far more tractable — describing "pick up the cup nicely" as a reward function is hard; demonstrating it fifty times is easy. The cost moves from reward engineering to data collection, which is exactly where simulation helps, because collecting fifty thousand simulated episodes is a scheduling question rather than a physical one.

LeRobot format

Lucky Engine records in a format compatible with LeRobot, the increasingly standard dataset format for robot learning. Compatibility matters more than it might seem: it means your recorded data works with existing training pipelines and published models without conversion, and it means datasets can be shared between labs. Deterministic high-rate capture means episodes are labelled and reproducible, which is what makes them trainable.

What makes a dataset good

  • Diversity beats volume. Ten thousand episodes of the identical trajectory teach less than five hundred varied ones. Randomize initial conditions, object positions, and targets.
  • Include recoveries. A dataset of only perfect executions produces a policy with no idea what to do once it's slightly off — and it will be slightly off immediately. Demonstrations that start from imperfect states are disproportionately valuable.
  • Record failures too, labelled as such. Knowing what not to do is information.
  • Keep provenance. Which engine version, which scene, which physics parameters, which policy generated it. A dataset you can't reproduce or interpret has a short shelf life.

System Identification — Chapter 9

Your simulated robot's parameters are guesses until you measure them. System identification replaces the guesses with numbers from the real machine, and it is one of the highest-leverage things you can do for transfer.

The idea

A MuJoCo model has parameters — motor gains, damping, friction, armature inertia — that came from a spec sheet or someone's estimate. Real actuators differ, sometimes substantially, and differ from each other. System identification excites the real robot with known signals, records how it actually responds, and fits model parameters that reproduce that response. The result is a simulation that behaves measurably more like your specific robot.

The workflow

# 1. See what presets exist for your robot
luckyrobots sysid presets --robot go2

# 2. Collect a trajectory from the REAL robot with an excitation signal
luckyrobots sysid collect --robot unitreego2 --signal chirp \
    --duration 15 -o traj.npz

# 3. Fit model parameters to the recorded response
luckyrobots sysid identify traj.npz -m go2.xml \
    --preset go2:motor -o result.json

# 4. Write the fitted parameters back into the model
luckyrobots sysid apply result.json -m go2.xml -o go2_calibrated.xml

A chirp is a sine sweep through a range of frequencies — it excites the system across its whole dynamic range in one short recording, which is why it's the standard choice. Fifteen seconds of well-chosen excitation tells you more than minutes of arbitrary motion.

Collection runs on real hardware — the safety rules apply Step 2 drives a physical robot with an excitation signal designed to provoke a wide dynamic response. That is exactly the kind of motion the G1 guide's safety chapter is about: robot on its stand, E-stop in reach, a second person watching, and start with conservative amplitudes. Sysid is a routine procedure, and it is still a procedure that deliberately shakes an actuator through its range.
From the field — calibrate before you train, not after The common and costly sequence goes like this: train a policy for a week against default model parameters, deploy it, watch it fail, then discover the simulated actuators were substantially stiffer than the real ones. Everything learned against the wrong dynamics has to be redone. Fifteen minutes of system identification before training would have prevented all of it. The general principle is worth carrying beyond this tool: measure the thing you're modelling before you invest heavily in the model. It's the same instinct as capturing a working requirements.txt the moment an environment works, or verifying joint indices before commanding a joint — a small, boring, cheap step that protects a large, expensive one. The boring step is almost always worth it, and it is almost always the one that gets skipped.

The Sim-to-Real Gap — Chapter 10

The most important chapter in this book. Simulation's danger isn't that it fails — it's that it succeeds convincingly, and lets you believe you're finished when you have only proven something about a model.

Where the gap comes from

SourceWhat simulation gets wrong
ActuatorsReal motors have backlash, stiction, current limits, and heat up. Simulated ones are ideal and tireless
ContactThe hardest thing to model. Real friction varies with surface, dust, wear, and temperature
SensorsReal ones are noisy, delayed, occasionally drop out. Simulated ones are perfect unless you make them worse
LatencyReal control loops have delay between sensing and acting. Sim is often instantaneous
Mass & inertiaCAD values differ from the assembled machine with its cables, dust, and yesterday's repair
The unmodelledCable drag, flex in a "rigid" link, a slightly loose bolt. Not in the model at all

Closing it

  • System identification (Chapter 9) — measure the real parameters instead of guessing. Do this first.
  • Domain randomization — vary mass, friction, gains, and latency randomly across training episodes, so the policy can't overfit to one exact model and has to be robust across a range. Counter-intuitively, a policy trained on deliberately imperfect physics transfers better than one trained on a single carefully-tuned model.
  • Sensor noise and latency — inject them deliberately. A policy that has only seen clean instant data is brittle to reality.
  • Action smoothing — penalize jerky commands in the reward. Real actuators can't follow discontinuous signals, and trying damages them.
  • Validate incrementally — don't go from simulation straight to a full hardware run. Test on the stand, then one joint, then slowly.

What simulation actually proves

Worth being precise about, because the honest version is still very valuable:

Simulation provesSimulation does not prove
Your code runs without crashingIt will work on hardware
Your signs and indices are rightYour gains are right for real actuators
The logic is soundIt's robust to noise and disturbance
The approach is worth tryingThe approach is finished
A whole class of bug is absentNo bugs remain

That left column is genuinely valuable. Eliminating crashes, sign errors, and index mistakes before touching hardware is most of what makes a lab session productive rather than a debugging exercise with a robot standing idle. The mistake is only in reading the left column as the right one.

From the field — simulate to eliminate, hardware to validate The productive division of labour is worth stating as a rule. Simulation is where you remove the bugs that would hurt. Sign errors, wrong indices, unstable gains, logic that crashes on the third iteration — catch all of it for free, at speed, repeatably. Hardware is where you find out whether it actually works. Those are different questions and neither environment answers the other's. Teams that skip simulation waste hardware time debugging things a laptop would have caught in seconds. Teams that over-trust simulation ship a policy that has never met friction and are surprised when it falls over. The good pattern is boring and effective: iterate fast in sim until nothing obviously wrong remains, calibrate the model against the real robot, add noise and randomization so the policy can't be precious, then move to hardware incrementally — on the stand, one joint, slowly — expecting to retune. Plan for that retuning as part of the work, not as evidence something went wrong.

Lab Exercises — Chapter 12

All of these run on a laptop. No robot, no lab booking, no risk.

Lab 1 — Connect and inspect

  1. Install the engine and the SDK in a fresh venv. Set LUCKYENGINE_PATH.
  2. Connect and print nq, nu, and every joint name.
  3. Explain in one sentence why nq and nu differ for a legged robot.
  4. List the available robots and policies.

Lab 2 — Step the world by hand

  1. Write a loop that steps 1000 times with zero action, printing one joint's position every 100 steps.
  2. Compute how much simulated time passed. Compare it with wall-clock time.
  3. Put a debugger breakpoint inside the loop (VS Code guide, Ch 9). Confirm physics is frozen while paused.
  4. Explain why this is impossible on real hardware.

Lab 3 — Drive a policy

  1. Acquire a locomotion policy slot and command a forward velocity.
  2. Stream state at 30 fps and log the robot's actual velocity.
  3. Plot commanded vs achieved velocity. Explain the tracking error.
  4. Compare this workflow with LocoClient.Move() in the G1 guide. What's the same?

Lab 4 — Actuators by name

  1. Command two named actuators to fixed targets. Confirm the right joints move.
  2. Now do it by index instead. Edit the scene slightly, re-run, and observe what breaks.
  3. Write up why name-based addressing is worth the extra characters.

Lab 5 — Reward design and hacking

  1. Build a LuckyEnv with a reward for forward velocity only. Train briefly with any RL library.
  2. Watch the rollout. Describe what it actually learned to do.
  3. Add an action_rate penalty and retrain. Describe the change in behaviour.
  4. Deliberately write a hackable reward and find the exploit. This is the most instructive part.

Lab 6 — Audit for privileged information

  1. Take any environment you've built and list every value in the observation.
  2. For each, name the real sensor that would provide it on a physical robot.
  3. Mark the ones with no real equivalent. These are your transfer risks.
  4. Rebuild the observation using only realizable inputs. Retrain. Compare the results honestly.

Choosing a Simulator — Appendix B

Lucky Engine is one of several reasonable choices. Picking well means knowing what each is actually good at.

SimulatorStrengthsCostsBest for
Lucky EngineMuJoCo physics + good rendering; editor; Python SDK; LeRobot outputNewer; smaller community than the incumbentsVision-based learning, dataset generation, teaching
MuJoCo (plain)Fast, accurate contact; the research standard; huge model libraryMinimal rendering; no editor; you build the toolingControl research, papers, headless RL at scale
Isaac SimPhotorealistic; GPU-parallel envs; strong sensor simulationHeavy; needs a serious NVIDIA GPU; steep setupLarge-scale RL with photorealistic vision
GazeboDeeply ROS-integrated; mature; large plugin ecosystemContact physics less accurate for legged workROS 2 systems, navigation, sensor pipelines
PyBulletTrivial to install; pure Python; good for teachingLess accurate; rendering is basicQuick experiments, coursework, prototyping
Pick for the question you're asking There's no best simulator, only a best fit for a question. Testing whether a control loop's signs are right? Anything works — use whatever installs fastest. Training a vision policy you intend to deploy? Rendering fidelity is now part of your physics and matters enormously. Integrating with an existing ROS 2 navigation stack? Gazebo's integration will save you more time than better contact modelling would. Writing a paper that others must reproduce? Plain MuJoCo, because everyone has it. Choose for the specific question, and don't be precious about using two — a fast crude simulator for iteration and an accurate one for validation is a perfectly sensible setup, and closer to how experienced teams actually work.
A closing word Simulation has quietly become the centre of gravity in robot learning — not because it's a substitute for hardware, but because it changes the economics of trying things. When an experiment costs a laptop-minute instead of a lab session, you run the experiment you were only going to think about, and that's where most progress actually comes from. Lucky Engine is a good instance of that shift: physics that's accurate enough to be worth trusting, rendering good enough for vision, and a Python interface plain enough to get out of the way. Use it to eliminate everything that would waste your hardware time, calibrate it against the real machine so it's modelling your robot rather than a generic one, and stay honest about the boundary in Chapter 10. Then go and find out what the real robot thinks of your ideas.
